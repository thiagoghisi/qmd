🔎 qmd

qmd is a local-first search runtime for markdown corpora. Files on disk stay the source of truth. SQLite, FTS5, sqlite-vec, and local GGUF models power retrieval. The strongest architectural move is not “hybrid search” in the abstract. It is the concrete pipeline: BM25 probe, typed query expansion, backend routing, reciprocal-rank fusion, chunk reranking, and score blending.

CLI MCP SQLite + FTS5 sqlite-vec node-llama-cpp Daemon + warm models

Executive summary

qmd is not a brain OS and it is not a wiki. It is a retrieval engine with a strong local-first stance. Markdown files live in collections on disk. A SQLite store builds two parallel access paths: full-document lexical search and chunk-level vector search. On top of that, qmd adds typed LLM query expansion, reranking, daemonized warm models, and agent access through MCP.

The single most important fact: BM25 is document-level. Vectors are chunk-level. That asymmetry is one of qmd’s biggest strengths today and one of its most important constraints for future contextual retrieval work.

Key architectural truth

qmd is built around a pragmatic belief: retrieval quality improves more from a disciplined, local-first, debuggable pipeline than from blindly throwing more vector magic at the problem.

Lexical remains first-class

FTS5 is not a fallback. It is a foundational retrieval path and the first probe in the hybrid pipeline.

LLMs are used surgically

Expansion and reranking are there, but gated. Strong BM25 signals can skip expensive expansion altogether.

Files remain primary

The store is derived. Source markdown on disk remains the truth that can always be inspected and reindexed.

Strong-signal short-circuit

If BM25 is already clearly right, qmd skips expensive expansion. This is one of the smartest product decisions in the repo.

Typed expansion

Expansion outputs are not generic paraphrases. They are typed as lex, vec, or hyde and routed to the matching backend.

Chunk rerank, not document rerank

qmd reranks best chunks per candidate document instead of entire bodies. That is a real performance and quality decision, not a cosmetic optimization.

qmd stores the same corpus in two representations: document identity and chunk semantics.

   │
   ▼

   ▼
document identity layer
   - documents(collection, path, title, hash, active)
   │
   ├── full-document FTS representation
   │     documents_fts(filepath, title, body)
   │

         content_vectors(hash, seq, pos, model, embedded_at)

Core search model

qmd’s retrieval logic is not “BM25 plus vectors.” It is a staged decision process. 

1. searchFTS() probes lexical strength
2. if strong enough, skip expensive LLM expansion
3. else expandQuery() emits typed variants:
     - lex
     - vec
     - hyde
4. backend routing:
     - lex  -> searchFTS()
     - vec  -> searchVec()
     - hyde -> searchVec()
5. reciprocalRankFusion() merges lists
6. choose candidate documents
7. re-chunk candidate bodies
8. choose best chunk per document
9. rerank best chunks
10. blend reranker score with RRF position
11. output snippets and paths

What qmd is optimizing

Retrieval quality under local constraints: low latency, bounded model cost, high debuggability.

What qmd is not doing

It is not maintaining compiled truth, entity pages, or living summaries. That is outside its architectural scope.

Collection and context model

qmd moved collections and contexts out of SQLite and into YAML. That was a strong product decision. 

~/.config/qmd/index.yml

global_context: optional string
collections:
  journals:
    path: /absolute/path/to/journals
    pattern: "**/*.md"
    update: optional shell command
    context:
      "/": "overall collection context"
      "/2026": "subtree context"

Important nuance: qmd already has a concept called context, but it means collection/path descriptions supplied by the operator. It does not mean LLM-generated chunk context. That naming collision matters for any future contextual-retrieval design.

Runtime flow — Hybrid query

This is the main intellectual core of qmd today. 

user query
   │
   ▼
searchFTS(query, 20)
   │
   ├── if top BM25 result is strong and clearly ahead:
   │      skip expansion
   │
   └── else:
         expandQuery(query)
            -> lex variants
            -> vec variants
            -> hyde variants
                  │
                  ▼
            route each variant to matching backend
                  │
                  ▼
             reciprocalRankFusion()
                  │
                  ▼
              top candidate docs
                  │
                  ▼
         chunk candidate bodies again
                  │
                  ▼
         pick best chunk per document
                  │
                  ▼
                rerank()
                  │
                  ▼
     blend reranker score with RRF position score
                  │
                  ▼
             final ranked results
Why this is good: qmd is not paying LLM cost blindly. It is using lexical strength as a gate, typed expansion as routing intelligence, and reranking only after a cheap candidate-narrowing stage.

Contextual retrieval — where it fits and where it doesn’t

This is the architectural question that matters most if qmd evolves.

Easy fit: contextual embeddings

Chunk-level vectors already exist. The cleanest low-risk experiment is to contextualize chunk text before embedding while preserving raw chunk text for display/debugging.

Hard fit: contextual BM25

BM25 currently indexes full documents, not chunks. Real contextual BM25 would likely require chunk-level lexical indexing, not just a tiny patch.

Architectural implication

The codebase supports a phased approach: contextual embeddings first, chunk-level BM25 only if the quality gain justifies a larger schema and retrieval change.

Current qmd
  BM25  -> full documents
  Vec   -> chunks

Contextual retrieval dream
  BM25  -> chunks with context
  Vec   -> chunks with context

Reality
  Vector-side contextualization: small / feasible
  BM25-side contextualization: bigger architectural change
Bottom line: qmd is more mature than a blank-slate PRD would assume. That means new retrieval ideas need to fit the actual document/chunk split instead of pretending the system is chunk-native everywhere.
